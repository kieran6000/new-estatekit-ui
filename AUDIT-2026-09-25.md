## 4. Found, not changed, ranked by how likely times how bad

**1. Anyone can become an operator (fixed on `dev`, NOT deployed).**
`verify-whatsapp-otp` is live with JWT verification off. Phone `+10000000000`
with code `0000` returns a session, and creates that user with
`is_operator = true`. From there: every lead, every agent, password resets,
ad controls. Separately, the 4-digit codes have no attempt limit and no expiry,
and they match *existing* accounts by phone. All 17 users have a phone set,
including yours, so any account can be brute-forced in about 9,000 requests.
**No sign of use:** the backdoor account doesn't exist, you're the only
operator, and there are no pending codes. Deploying the 410 stubs closes it
(§5, step 1). This is also where the duplicate `@phone.estatekit.co` accounts
came from: this function uses a different email domain from the password login.

**2. Share-link leak (fixed on `dev`, needs §5 steps 3 and 5).**
It's worse than we thought yesterday. The `leads` policy is "any lead that has
an unexpired token", and it **doesn't check which token you hold**. So
`select * from leads` with the public key returned about 286 leads, no token
needed. Any signed-in agent could read other agents' leads the same way. And
since the token table is public too, anyone could **write** to those leads
(log outcomes, add notes, mark calls). Tokens get created for every website
lead (24h), every automation WhatsApp (7 days) and every Discord card (30
days), so it's a rolling window over your freshest leads.

**3. Ad controls and ad data open to anyone (fixed on `dev`, §5 step 2).**
See `0b14879` and `9be5e10`. Ad IDs aren't secret: the `{{ad.id}}` macro puts
them in landing-page URLs.

**4. WhatsApp alerts lost but logged as sent (fixed on `dev`, §5 step 4).**
3 in the 24h I looked at. There's a knock-on I didn't fix: OTP and any other
sender share the same TextMeBot account, so they can still collide with
automation sends. Automations now retry; nothing else does.

**5. Anyone can trigger the backend jobs, and burn your Facebook quota.**
`run-automations` and `sync-fb-leads` are called by cron with no auth header,
so anyone can call them too. `sync-fb-leads` with `sinceDays: 0` pages through
every lead ever collected. `get-fb-form` has a `force` flag that skips the
cache. `discover-fb-pages` calls `me/accounts`, your most expensive call.
Hammering any of these trips Facebook's rate limit, and the backoff then pauses
**everyone's** lead sync for 20 minutes at a time.
*Fix:* a `CRON_SECRET` checked by the two cron functions, with the cron commands
sending it (both need changing together). A signed-in check on `get-fb-form`,
`list-fb-forms` and `discover-fb-pages`. Not done: it needs a cron change in the
database plus coordinated deploys.

**6. The Facebook page picker shows every client's page names to any agent.**
My own design mistake from yesterday. `discover-fb-pages` returns every page
our tokens can see (names and ids, not tokens). *Fix:* show the picker only to
operators (`useOperatorPreview()` exists now), and add an operator check in the
function.

**7. Public lead pages are heavy.**
Siva's page downloads a **991 KB logo and a 2.6 MB photo**, stored as base64
inside the page row, before the form appears. The public page selects `*`, so
it also pulls the photo, which only shows on the thank-you screen. Add a 1.4 MB
JS bundle and it's about 5 MB on SA mobile data. Anita: 1.6 MB. Juani: 1 MB.
*Fix:* move images to Supabase Storage at around 400px, and have the public
page select only the columns it uses.

**8. Every `/p/` link shared on WhatsApp shows the generic preview.**
Title "EstateKit — Real estate leads, handled", and `og:image` is
`/favicon.svg`: relative, and SVG, which WhatsApp and Facebook won't render.
It's a single-page app, so crawlers never see the agent's headline or photo.
*Fix:* a small Vercel function for `/p/*` that injects the page's own title,
description and an absolute JPG `og:image`. It's the same mechanism the old
repo used for the pixel.

**9. The public lead page's failure modes.**
- A failed page or pipeline fetch shows **"This page isn't available"**, the same
  bug class as last night. A patchy connection makes a paid ad click look like
  a deleted page. Only 1 retry.
- A failed questions fetch **silently shows the form with no questions**, so no
  qualifying answers and no disqualification.
- A failed submit is swallowed (`.catch(() => {})`), and the visitor still sees
  "Thanks, we'll call you". **The lead is lost with no trace.** I compared
  submit events against saved leads for 14 days: no page has more submits than
  leads, so **there's no evidence it's happening**. But nothing would tell you
  if it did.
*Fix:* await the submit behind a spinner, and on failure show "Couldn't send.
Tap to try again" with the answers kept. I didn't change this: it's the page
that earns the money, and you should test it yourself.

**10. Hardcoded Discord webhook in `run-automations`** (private repo, and in git
history). Move it to a secret. Rotate it if more people have repo access than
you think.

**11. Silent sync failures, and 5,644 wasted inserts a day.**
The sync re-inserts every lead from the last 3 days on every run and gets a
409 each time, then runs an extra update per duplicate. pg_net gives up waiting
after 5s, so each run's result (including any form that failed to fetch) is
thrown away. A broken form would be invisible. *Fix:* select the existing
`fb_lead_id`s first; `console.log` the summary; raise the cron's
`timeout_milliseconds`.

**12. `sold_listings` is per agent, not per page.** Hannaford's listings show on
all 3 of your demo pages. *Plan (add-only):* add a nullable `page_id`, where
null means "all my pages", as today. Then the public page filters with
`page_id = this page or page_id is null`.

**13. No ownership check when creating a lead source.** `addLeadPage` accepts any
`pipelineId`, which is how last night's bad row happened. Validate that the
pipeline belongs to the agent. Not done tonight for lack of time.

**14. Deploy script and verify_jwt.** `deploy-functions.sh` passes
`--no-verify-jwt` for every function. Keep that only for functions that
genuinely must be public (`public-submit-lead`, `track-page-event`,
`track-activity`, `fb-lead-webhook`, and the cron targets until item 5 is done).

## 8. Where the prompt was wrong

- **"sync-fb-leads reads `b.formId` but callers send `onlyFormId`": not a bug.**
  It reads `b.formId` into a variable called `onlyFormId`, and the only caller
  sends `formId`.
- **`is_operator()` executable by anon: leave it.** It only ever returns the
  caller's own flag, which is false for anonymous users. Several policies call
  it for every role, so revoking it risks breaking anonymous reads for no gain.
- **`fb_page_tokens`, `otp_codes`, `phone_otp_codes` with RLS on and no
  policies:** that's an intentional deny-all. Every reader uses the service
  role. Fine.
- **Yesterday I said "every lead is readable".** The real figure is about 286,
  but it's worse in kind: no token needed, and writes are possible too.
